## 1. Objective / success criteria

Make `dsh-recursive-mode` a **legible, enforced, crash-resumable** recursion engine over a file-backed control plane.

**What this objective deliberately does NOT say.** An earlier revision read *"a durable, native, resumable recursion engine rather than a single-threaded controller that reconstructs state from the filesystem"*. Two audits showed both halves of that contrast to be wrong, so they are struck:

- **"single-threaded" is not a defect here.** Measured against `src/`: zero `Promise.all`/`race`/`allSettled`, zero uses of the jobs service, zero worker threads or child processes, three timer sites (all client SSE/polling), and 22 synchronous `writeFileSync` sites. The plugin is single-process, single-writer, with no concurrency to coordinate. A durable queue exists to decouple producers from consumers under concurrency, backpressure, or multi-process contention; none is present. The durable-queue role is already filled by **DSH's own turn loop**.
- **"reconstructs state from the filesystem" is the design, not the weakness.** Markdown artifacts, hash-chained receipts and git *are* the durable, diffable, human-reviewable substrate. Both audited systems pay real costs to approximate this: Effect's event log is `@stability unstable` with no event versioning and no snapshots, and Tardigrade's default checkpointing refuses to run while work is pending and never truncates its log. Owning the source of truth in files is the plugin's main structural advantage.

The genuine gaps are therefore **enforcement that does not fire, contracts that are not legible, in-flight work that is not recorded, and recovery that is not bounded.**

**A prior condition precedes all of them: the baseline is currently RED.** `pnpm typecheck` fails at 12 sites and five spec files fail (see §7.0). No criterion below is measurable until T-1 has made the tree green, because every item's acceptance test is "the suite stays green" and the suite is not green today.

Concretely, "done" means:

1. **The control plane stays the single source of truth, and stays readable.** Requirements, plans, evidence and state live in repo Markdown. No second store, no manifest cache, no client-side store. Every derived fact is folded from files on demand.
2. **Enforcement is real and auditable.** The tool guard receives the *active run*; `validateTransition` and `detectTamper` are on the live path rather than exported-and-uncalled; every gate decision is recorded with its reason; a `Status: LOCKED` artifact cannot be written without an explicit reopen.
3. **The phase contract is legible before it fires.** A human — and the model — can read in advance what the current phase requires, which rule will match a proposed tool call, and what the next legal transition needs. No prompt/gate contradiction.
4. **A lock only happens at a quiescent point.** A phase cannot lock while delegated or repair work is unresolved, and in-flight work is recorded so a crash mid-audit resumes rather than restarts.
5. **Work is bounded, and stuck work terminates loudly.** Audits, repair rounds, delegations and tool results all have explicit caps; a loop that stops making progress ends and requires an explicit resume rather than retrying or giving up silently.
6. **The prompt is cheap to re-send.** A byte-stable prefix carries the contract; a digest names it; only a per-turn tail varies.
7. **The dependency model matches reality.** Prerequisites, addenda and receipt invalidation form a **DAG**, not a flat sequence indexed by array position.
8. **The recursion compounds — memory is actually read and written.** Delegated work is verified against real files and the real diff; **prior-run memory is injected when a run starts** (T29) and **a completed run's learnings are extracted when Phase 8 locks** (T30). Today *neither* happens: the memory plane is created, linted, and otherwise untouched. See §3 Temporal.

#### 4.0 The substrate rule — files vs. `ctx.storageDomain`

Several items below need somewhere to keep state that is neither an artifact nor a session event. DSH now ships the right facility, and using it correctly matters because it sits close to this repo's most important principle.

**`ctx.storage` / `ctx.storageDomain`** (`packages/storage/storage`, backends `storage-json` and `storage-sqlite`) is a host-side durable store whose stated purpose is *"application state that must survive restarts **without becoming session events**"*. It registers no tools, injects no prompts, and **writes no session events** — so it does not touch the zero-emission invariant. `kv` is the only data shape. It is optional: a composition must mount the hub plus a backend and the domain form, so the plugin must degrade gracefully when it is absent, exactly as it already does for `goals`, `skills` and `agentTeams` (`backend-not-found` / `form-not-mounted` are the failure modes).

**The rule, which protects "files are the single source of truth":**

- **Files stay authoritative.** Anything that *is* the workflow — artifacts, receipts, locks, addenda, the control plane — lives in the repo and is reviewable in git. Never mirror it into storage.
- **`ctx.storageDomain` is for caches and indexes that can be thrown away and rebuilt.** A fold cache, an operation-identity index, a guard-decision log: losing these costs performance or evidence, never correctness.
- **Derived beats stored where derivation is cheap.** Per T18, pending work is *derived from the run directory*, not recorded — so it needs no store at all. Reach for `ctx.storageDomain` only where derivation is genuinely too expensive to repeat (T21) or where a fact cannot be re-derived from files (T19).
- **Degrade, never depend.** No item may make a store mandatory. Absent storage → recompute, and say so.

### T33 — The lint section parsers cannot read a document's FINAL section (`\Z` is a literal `Z` in JS) · **done**

- **Why, with proof.** `getHeadingBody` (`ts-lint.ts:137`) and `getSubheadingBody` (`:145`) end their lazy capture with the lookahead `(?=^[ \t]*##\s+|\Z)`. That `\Z` was carried over from the canonical Python implementation, where `\Z` means *absolute end of string*. **In JavaScript `\Z` is an unrecognised escape and degrades to an identity escape, i.e. it matches a literal `Z` character.** Verified by execution: `/\Z/.test('nothing here') === false` but `/\Z/.test('a Z here') === true`. Consequences, both verified:
  - If the section is followed by another heading, the first alternative matches and everything works — which is why the bug hid for so long.
  - If the section is the LAST one in the string handed to the helper, the lazy capture can only terminate at a literal `Z`. With no `Z` present the match fails outright and the helper returns `''`. Measured: `getHeadingBody('## First\nbody one\n## Last\nbody two', 'Last') === ''`; appending a dummy section after it returns `"body two"`; a trailing newline does not help.
- **Why it matters here — it is the THIRD side of the T25 contract.** A section's *last* sub-heading is therefore always invisible. In `lintSubagentActionRecordFile` that means `getSubheadingBody(claimedFileImpact, 'Reviewed')` — `Reviewed` being the final sub-heading of `## Claimed File Impact` — always reads empty, so `claimedFileRefs.size === 0` and the record fails `Claimed File Impact must cite at least one created, modified, reviewed, or relevant untouched file`. **A read-only review delegation — a reviewer that creates and modifies nothing, which is this plugin's primary delegation use case — can therefore never produce a record the repo's own linter accepts**, no matter how correct the writer is. Independently reproduced by the orchestrator with a hand-built record (`reviewedFiles` set, `createdFiles`/`modifiedFiles` empty).
- **How it surfaced:** the T25 implementer hit the same root cause from the other direction and worked around it by appending a trailing `## Record Provenance` section (commented "LOAD-BEARING, do not delete") so `## Verification Handoff` is no longer the final section, and by keeping a `Z`-bearing ISO timestamp last in `## Metadata`. The workaround is honest and documented, but it only covers the whole-section case, not the last-sub-*heading* case.
- **What:** translate the anchor faithfully — `\Z` (Python, absolute end of input) is `(?![\s\S])` in JS, not `\Z`. Apply it in both helpers. Then re-examine the two workarounds and delete whichever are no longer needed.
- **⚠ Do not treat the parity goldens as an oracle for this change.** The goldens were captured in the old tree and (measured) contain four `Missing or empty section` verdicts whose headings are **genuinely absent** from the fixture, so they do not discriminate the bug either way. Because the canonical implementation is Python — where `\Z` is correct — fixing the port should move it **toward** canonical parity. If a golden does shift, analyse which behaviour is canonical before regenerating anything, and record the decision.
- **TDD Mode:** `strict`.
- **RED:** `tests/section-parser.spec.ts` — a heading followed by another heading reads its body; the **final** heading reads its body; a body containing a literal `Z` is not truncated at it; the final sub-heading of a section reads its body; a genuinely absent heading still reads `''`; a heading whose body is only `- none` reads `- none`.
- **GREEN:** `src/ts-lint.ts` (both helpers), plus whatever workaround comment in `src/delegation.ts` becomes obsolete.
- **Acceptance:** every section and sub-section of a document is readable regardless of its position; a read-only review delegation produces an action record the repo's own linter accepts with **zero** violations; `lint-parity` is green or its shift is explained and recorded.
- **Blast radius to check:** 63 call sites of the two helpers inside `ts-lint.ts` — many apply to documents whose last section is exactly the one being read (e.g. `## Diff Basis For Later Audits`, `## Plan Drift Check`), so expect previously-empty reads to become populated. Run the full suite and the parity goldens before believing the change is contained.
- **Evidence:** this session — execution probes of `/\Z/`, of `getHeadingBody`/`getSubheadingBody` on synthetic documents with and without a trailing section, and of `lintSubagentActionRecordFile` over a `writeActionRecord` output carrying only `reviewedFiles`.

- **RESULT — done, and the blast radius turned out to be nil.** RED first (`tests/section-parser.spec.ts`, 14 tests, **7 failing**), which also sharpened the diagnosis in two ways the item spec had not stated:
  1. **There are FOUR affected regexes, not two.** Besides `getHeadingBody` and `getSubheadingBody`, `extractPathsFromNamedField` (`:287`) and `getNamedFieldText` (`:302`) carry the same anchor on their NAMED-FIELD block form — so a named field block that is the last thing in its section was equally unreadable. That is the same class of hole the T25 writer had to work around by emitting fields in a safe order.
  2. **The truncation is not confined to final sections.** A body is cut at its first literal `Z` *wherever it appears*, so an ISO timestamp mid-document truncates the section: measured, `## Metadata` containing `- Timestamp: 2026-01-01T00:00:00Z` was read as `'- Timestamp: 2026-01-01T00:00:00'`, silently dropping every field after it. The final-section case is just the degenerate one where no `Z` exists at all and the capture fails outright.

  - **Blast radius: measured, and bounded.** The item spec warned that 63 call sites could start reading content that previously read as empty, and that the parity goldens were not a reliable oracle. ### T35 — Delegation is ALWAYS continuable; one-shot must be asked for · **done — added mid-Sprint-2**

- **Why (operator directive, and it is the point of verification).** Review that cannot be followed by repair is just a complaint. A **one-shot child is not resumable** — the harness rejects a resume with `subagent cannot be resumed` — so delegating one-shot silently forfeits the ability to send a failed review back to the agent that did the work. A **continuable child has ONE durable Session across activations**, so a `REVISE` reaches the SAME child with its working context intact, instead of spawning a fresh one that must re-read the whole handoff to rediscover what it already knew. This is the mechanism the harness itself provides for exactly this purpose (`startContinuable` → `followup` to the same durable child), so the plugin should be on it by default rather than by request.
- **The rule.** `delegateReview`'s `mode` defaults to **`continuable`**. An explicit `mode: 'one-shot'` is the ONLY way to give up the repair path, and is reserved for a caller that genuinely discards the result. Two hard preconditions remain, because they are capability facts rather than preferences: the continuable path needs the `awaitRoundResult` observer (the parent-side settlement seam) and the exact live `parent` Agent (followup is authorized by object identity). When either is absent the delegation still happens but the loss is **NAMED** — `delegationMode: 'continuable-unavailable'` — rather than hidden behind a generic success.
- **TDD Mode:** strict.
- **RED:** `tests/delegation-mode.spec.ts` — an omitted mode uses the continuable lifecycle and never calls `start()`; `mode: 'continuable'` behaves identically; only an explicit `mode: 'one-shot'` calls `start()`; a provider without the continuable capability reports `continuable-unavailable`.
- **Substrate:** none.
- **Acceptance:** no delegation in this plugin can lose the repair path without saying so.
- **Evidence:** `tests/delegation-mode.spec.ts` (5 tests; RED captured at 2 failing against the pre-T35 behaviour in `evidence/logs/red/T35-default-mode-red.txt`); full suite **55 files / 410 tests**; typecheck 0.

- **RESULT — done, and it exposed that the seam had never been exercised at all.** The RED run is the finding: with the old branch condition, the spec fails with `expected [ 'start' ] to include 'startContinuable'` — i.e. **every** caller that omitted `mode` (which was all of them) took the one-shot path. The default is now continuable, the actual mode is reported as `delegationMode` (`continuable` | `one-shot` | `continuable-unavailable` | `none`), and the action record's `executionMode` is derived from what ACTUALLY ran rather than what was requested.
  - **Second finding, and it is the real one: `delegateReview` HAS NO CALLERS.** Not in `src/`, not in `tests/`, not in `scripts/` — the T4 continuable loop is fully implemented, covered at the `delegateContinuable` level, and reached by nothing. So flipping the default changes the behaviour of a path no production caller walks yet, and this spec is that method's **first** coverage. The directive is therefore only half-satisfied by the default: delegations must also be **wired to this entry point** for a failed review to become a repair. Recorded as the next item rather than folded in, because wiring changes which mechanism drives review (this seam vs. the `agentTeams` board used by `recursive_audit_team`) and that choice deserves its own decision.
  - **A caveat on the fallback, stated plainly:** when the continuable seam is missing, the delegation still returns a usable result and the review still happens — only the *repair round-trip* is unavailable. `continuable-unavailable` is therefore a capability degradation, not a failure, and a caller must not read it as one.
  - **Whole-repo note:** the same reasoning applies to any future delegation path in this plugin — including the `agentTeams` board, which can carry a repair instruction but only to a **task**, not to the session that did the work. That asymmetry is worth remembering when the two mechanisms are reconciled.

### T36 — Wire delegation to the continuable seam so a failed review becomes a repair · **done**

- **Why.** T35 made `continuable` the default and then found that `delegateReview` **has no callers**, so the rule governs a door nothing walks through: the plugin still does not *use* continuable subagents for anything. The operator directive behind T35 — *the main agent must be able to message a child whose work failed review and tell it to re-do or repair* — is satisfied by the library but not by the product until a caller drives it. Verification that cannot be followed by repair is just a complaint, and today the plugin can only complain.
- **The decision this item must take first.** Two mechanisms can carry review work, and they are not interchangeable:

  | mechanism | carries a repair to | state after a failed round |
  |---|---|---|
  | continuable seam (`runtime.delegateReview` + `ctx.subagents`) | the **session** that did the work | child keeps ONE durable Session; a `followup` reaches it with its context intact |
  | `agentTeams` board (`recursive_audit_team`, `src/teams-loop.ts`) | a **task** | work is re-taskable, but the agent that produced it is not addressable |

  Only the continuable seam can tell the *agent* "your submission failed, fix it". The board can only say "this work is unfinished". Because the plugin's whole posture is that a phase is not done until an independent party says so, and that a rejection must be actionable, **the seam is the mechanism for phase review**; the board stays for parallel work decomposition. Record this choice on the item when it is made.
- **The real obstacle, named so it is not rediscovered.** The harness has **no parent-side "await settlement" promise**: a child's verdict arrives on a LATER turn as a durable user message (`source.kind === 'subagent-settled'`), which is exactly why `recursive_audit_team` is designed as one transition per call. So the caller must be **turn-shaped** — start the round, park, and resume on the next turn when the settlement notice lands — or the loop runs only where a caller already owns the turn. Any design that blocks inside one tool call is guessing at a settlement it cannot observe, which is why `delegateContinuable` refuses to fabricate one.
- **What.** (1) Bind the `awaitRoundResult` observer to the live parent Agent plus the real settlement notices, so a round is observed rather than assumed. (2) Give the review path a reachable caller that drives `delegateReview` in continuable mode — most likely the phase-review step the tools already expose, made turn-shaped. (3) Drain the child on closeout with the correct authority (`drainContinuableChildren` needs the live parent, never a `childId`, which is a different credential). (4) Report `delegationMode` through to whatever the agent sees, so `continuable-unavailable` is visible rather than swallowed.
- **TDD Mode:** strict.
- **RED:** (planned) `tests/delegation-wiring.spec.ts` — a phase review driven end to end that forces a **REVISE** round: `startContinuable` establishes ONE child, the repair `followup` addresses the **SAME child id**, `start()` is never called, `delegationMode` is `continuable` (never `continuable-unavailable`), and after settlement the child is still addressable — the property the whole item exists to buy.
- **Substrate:** none. The child's durable state is its SESSION (harness-owned); the plugin's `handoff.md` / `brief.md` / `reply.md` remain the human-readable parallel record, and must not be mistaken for the durable one.
- **Acceptance:** a failing phase review produces a repair followup to the same durable child, and no delegation on this path can lose the repair capability silently.
- **Depends on:** T35 (done — the default), T4 (library done). **Interacts with:** T19 (identity for retries is vacuous until retries are reachable) and T20 (the no-progress bound assumes a loop that runs).
- **Evidence:** T35's finding that `delegateReview` had zero callers; the harness behaviour that a one-shot child is not resumable, so this is the only path that can carry a repair.

- **⚠ VERIFIED CONSTRAINT — the obvious observer is FORBIDDEN, and the premise was checked before building it.** The natural implementation of `awaitRoundResult` is to scan the parent's session log for the `subagent-settled` notice. That is prohibited: DSH's Agent Note *"Deprecate synchronous reads of arbitrary Session events"* (`implemented`, 2026-09-09) states that `Session.eventAt()`, `Session.snapshotEvents()` and `Session.ownEvents()` are deprecated and — quoting it — *"existing logic may remain unmigrated for now, but **new calls are prohibited**"*, that *"new aliases or wrappers that expose the same synchronous historical access are prohibited as well"*, and that *"copying a waiver to a new production call violates this policy"*. It is enforced by an **executable lint check** that *"rejects unwaived production reads"*. The note's prescribed replacement is to *"process the delivered current event"* or read **maintained projection state**. So the observer was designed the sanctioned way instead: recognise the settlement **at delivery time** (`ctx.on('session/event', …)`, the same seam the projection registry itself subscribes to) and record it in the run's own **file** state — which is the plugin's zero-emission, file-derived architecture and also the shape the note recommends, since history reads would make ordinary logic depend on storage.
  - **This also re-frames T5.** T5 is `SETTLED — not adopted` for projections because adopting them would require the plugin to EMIT events. That reasoning holds for *emission* and is untouched here: T36 only *consumes* a delivered event and writes a file. Worth remembering if projections are revisited — the prohibition is on new synchronous *history reads*, not on listening.
- **PROGRESS.** Implemented and green: `src/settlement.ts` — `settlementFromEvent` (recognise a notice from one delivered event, pure, safe on any event), `recordSettlement`/`readSettlements`/`readSettlement` (append-only per-run log at `subagents/settlements.jsonl`), `settlementResult` (map a notice to the loop's result shape, deliberately NOT asserting `success` from the summary — a notice reports how the turn ENDED, not whether the work passes, and defaulting to success would let a stopped child read as an approved review), `settlementRoundObserver` (returns **null** while nothing has landed, which is the loop's documented "not yet" signal, so the caller parks and resumes on a later turn with the SAME child id), `captureSettlement` (record-on-delivery), and `runDirForChild` (which run owns this child, derived from the `child-<id>` directory the delegation wrote — **ambiguity returns null rather than guessing**, because filing a settlement into the wrong run would attach one run's evidence to another run's chain, while a miss only costs a "no settlement yet" the loop recovers from). Covered by `tests/settlement.spec.ts` (18 tests).
  - **The `session/event` hookup is LIVE and PROVEN, not merely written.** `src/index.ts` subscribes and routes a delivered notice through `runDirForChild` → `recordSettlement`, rejecting non-settlements with a cheap shape test BEFORE any filesystem work (the listener sees every event in every session). `tests/settlement-wiring.spec.ts` mounts the real plugin and delivers events the way the harness does, and it asserts the IGNORE cases as carefully as the happy path: a non-settlement writes no log file at all, a settlement for an unowned child files nothing, a session with no workspace files nothing, and the listener never throws whatever it is handed — it rides the hot path of every event and must not break the session it observes.
- **REMAINING for T36.** ONLY the caller's outermost layer: a `recursive_review` tool that resolves the run/phase/role and the artifact, dispatches through the driver below, and returns the outcome to the agent. **Everything under it is shipped and tested**, including the two things a caller cannot supply for itself:
  - **`src/review-round.ts` — the turn-shaped driver.** `advanceReview` is designed to be called ONCE PER TURN, like `recursive_audit_team` advances the teams board one transition per call, because a review cannot be one call that waits. It reads the durable review state, resumes the recorded child (never re-establishing it), and maps the loop's result to one of `reviewing | revised | approved | rejected | unavailable`. The state file (`subagents/<delegationId>/review-state.json`) is what lets the child survive between turns; a finished review is CLEARED so it cannot be resumed by accident, and a corrupt one reads as "no known review" rather than crashing.
  - **`parked` threaded through `delegateReview`.** The loop already reported a parked round, but the runtime flattened it into `error` — so a caller could not tell an ordinary wait from a real failure. It now returns `parked` + `parkedReason` with `error` left null: waiting is not failing, and an unobserved round is never an approval.
  - **The fail-closed verdict is enforced at the driver, not just offered.** A round whose result says `accepted` but whose `reply.md` cannot be read as an APPROVE is reported as `revised` — never approved "on a technicality" — and the child is KEPT so the repair can still reach it, because losing the child is losing the repair path.
  - **`unavailable` names the degradation instead of hiding it:** a one-shot fallback means the review happened WITHOUT the repair path, and the message says exactly that.

### T37 — The suite is INTERMITTENTLY red (observed once, not yet reproduced) · **done — it was T19's guard, not a mystery**

- **Why.** Every green claim in this plan rests on `pnpm test` being deterministic. During T19's part-1 commit the full suite reported **`1 failed | 509 passed (510)`**, and five subsequent runs (three consecutive, then two more) reported **510/510**. So a real failure occurs at a low rate and was not captured: the failing spec's NAME was lost because the check that ran it only matched the summary counts. That is the worst kind of red — it costs a full re-run to disprove and it teaches a reader to ignore a failure.
- **What.** Reproduce it, then either fix the cause or, if it is a genuinely environment-dependent test, make that dependence explicit and deterministic. Candidate suspects, in order: (1) the `tests/global-setup.ts` mtime stamping of fixtures, since several specs depend on file **mtime ordering** and a stamp racing a test's own writes would flip a "latest run" resolution; (2) `tests/identity.spec.ts`'s three runtime cases, which are the newest and use `new Date()` timestamps plus real `lockArtifact` writes; (3) the `fs/observed` guard-log path, which writes from a synchronous listener while specs run in parallel.

- **TDD Mode:** strict — the fix must come with a test that fails deterministically without it, or an explicit documented reason the test is environment-bound.
- **Acceptance:** either the flake is gone, or its cause is named and bounded in this item.
- **Evidence:** the pre-commit run at `e7f55c4` (`1 failed | 509 passed`), versus five subsequent 510/510 runs. Recorded rather than dismissed because a suite that is red one run in six silently weakens every other item's verification.

- **RESULT — FOUND AND FIXED, and it was far worse than a flake: it was a 50% NONDETERMINISTIC GUARD.** Twelve instrumented runs (capturing the failing spec and test NAME, which is the method fix this item demanded) gave **6 failures in 12** — not the 1-in-6 the first sighting suggested — and every one was the same test *I had added in T19 the round before*:
  `× T19 — reopen identity at the real seam > BOUNDARY: reopening an UNCHANGED re-locked artifact is a repeat` → `promise resolved … instead of rejecting`.
  - **ROOT CAUSE.** The reopen identity was keyed on the artifact's **`LockHash`**, and `lockHashFromContent` → `normalizeForLockHash` normalises away only the `LockHash` line — **not `LockedAt`**. `LockedAt` is wall-clock truncated to the **second**, so locking byte-identical content twice produces *different* hashes whenever the clock crosses a second boundary. The guard therefore fired or did not fire depending on timing: within one second it recognised the repeat (test passes), across a boundary it did not (test fails). A guard whose behaviour depends on the clock is not a guard, and the failure rate is a property of the machine's speed, not of the code.
  - **THE FIX.** Key on the artifact's **BODY** — its content with the lock fields (`Status`, `LockedAt`) normalised out, hashed with the existing `lockHashFromContent`. The body is stable across a re-lock of identical content and changes as soon as the author changes anything that matters, so: a retry after a FAILED reopen is still recognised, `reopen → fix → lock → reopen` still works, and an unchanged re-lock is deterministically a repeat. Verified **0 failures in 10 consecutive identity runs** and **0 in 5 consecutive full-suite runs**, against 6-in-12 before.
  - **WHY THIS MATTERS BEYOND THE TEST.** The failing test was not a test bug: it was the only thing standing between a timing-dependent guard and production. T19's boundary case, written to *document* an awkward edge, is what exposed it — the value of pinning a boundary rather than describing it in prose.
  - **The suspects this item listed were WRONG, and are recorded as such:** the fixture mtimes are safe (`global-setup` stamps them 14 days apart), the shared fixture repo is read-only in every spec that touches it (`lock.parity` writes to a temp dir), and the `fs/observed` guard-log path was not involved. ### T38 — Move the built-in tool guard ONTO the hook registry (T27's third clause) · **done**

- **Why it is separate from T27.** T27's acceptance — *a sibling DSH plugin can participate without patching this one, and ordering and failure behaviour are declarative* — is met: the registry exists, is exposed on the mounted service, and the `pre_trigger` chain runs in the REAL `tools/pre-execute` path, so a sibling vetoes an actual tool call. T27's GREEN adds a third clause, *"re-express the plugin's own enforcement as built-in hooks"*, which is **architecture rather than capability**: a built-in and a sibling would become peers on the same chain instead of one being privileged code. It was deferred rather than attempted at the end of a round because it is a ~70-line move straight through `guard-path.spec.ts`'s pinned sha256 contract, and a half-applied move there leaves the tree red — which is worse than an honestly scoped remainder.
- **What, precisely.** (1) Extract the listener body — root/runId resolution, `evaluateToolGuard`, `coerceAskToDecision`, the guard-log append and the tamper check — into a function returning the guard's `ToolGuardDecision`. (2) Register it as a built-in hook: `recursive.hooks.register('pre_trigger', { name: 'builtin-tool-guard', priority: 0, onError: 'fail_closed', run })`, returning `deny` for a denial and `continue` otherwise, with the **full decision object carried as an annotation** so `ask`/`allow` and their `warn`/`rule`/`transition` fields survive untouched. (3) The listener then runs the chain, and: if the chain denied and the denier is NOT the built-in, it returns a SIBLING denial (today's behaviour); if the built-in denied, it returns the guard's ORIGINAL object verbatim; otherwise it applies the annotated decision exactly as now.
- **Why priority 0 for the built-in.** Siblings with a higher priority run FIRST and can pre-empt the guard cheaply, which is the point of participation; the guard remains the baseline that runs when nobody objects.
- **TDD Mode:** strict. **RED:** extend `tests/hook-registry.spec.ts` — with the built-in registered, a tool call behaves identically to today (the live no-hook test already asserts the shape); a sibling with higher priority short-circuits BEFORE the guard runs; a sibling that fails `fail_closed` denies (the built-in's own policy).
- **The contract that must not move:** `tests/guard-path.spec.ts` (10 tests, sha256-pinned) must pass **byte-identically**, and the guard's `ask`-coercion must stay key-frozen because `coerceAskToDecision`'s output is asserted with an exact `toEqual`. If either moves, the refactor is wrong rather than the test.
- **Acceptance:** the plugin's own enforcement is a hook like any other, and `guard-path` is unchanged.
- **Evidence:** T27's parts 1 and 2 (the registry and the live seam), and the reason recorded there for not attempting the move in the same round.

- **RESULT — done, and the pinned contract did NOT move.** The guard body was extracted from the listener into `runToolGuard` (root/runId resolution, `evaluateToolGuard`, `coerceAskToDecision`, the guard-log append and the tamper check all stay together, so moving the call site cannot lose a side effect), and registered as `pre_trigger` hook **`builtin-tool-guard` at priority 0** with `onError: 'fail_closed'`. A sibling with a higher priority now runs FIRST and can pre-empt the guard cheaply, which is what participation was supposed to mean.
  - **The guard's object is returned VERBATIM.** The hook carries the full decision as an annotation and the listener returns that object unchanged, which is why `guard-path.spec.ts`'s 10 sha256-pinned tests pass **byte-identically** — the evidence that this was a move and not a rewrite.
  - **⚠ A subtlety that would have been a bug: the decider is checked by NAME, not by the built-in's presence.** A sibling with a LOWER priority than the guard runs *after* it, so "the built-in is in the trail" does not mean "the built-in decided" — a sibling's denial there would otherwise have been swallowed and the guard's allow returned. The listener inspects the LAST entry in the trail instead.
  - **A failing guard is reported as a failure, not as a silent allow** (`the tool guard failed: …`), and an impossible "no decision" state fails CLOSED — "we could not decide" is not permission.
  - **⚠ MY TEST PREMISE WAS WRONG (the 7th such correction in this plan), and I measured instead of guessing.** Two new tests asserted the guard would DENY an out-of-order lock; both failed with `continue`. A probe against the real functions showed the guard returns **`ask`** there, and under the default **advisory** mode `coerceAskToDecision` turns an `ask` into an **allow that carries the warning** — so the chain correctly continued. The tests needed `toolGuards: 'strict'`, and the probe's finding is now pinned as its own case: *in advisory mode the same call is allowed with the guard's warning kept*.
  - **Evidence:** `tests/hook-registry.spec.ts` (33 tests, of which 5 are T38's), `guard-path.spec.ts` 10/10 unchanged, full suite **66 files / 579 tests** green on 3 consecutive runs, typecheck 0, build 0.

## 8. Sequencing rationale

- **T-1 first, ahead of everything — this is the change from the previous revision.** The plan previously assumed a green baseline and put the dependency rebase first. The baseline is not green: `pnpm typecheck` fails at 12 sites and five spec files fail. Because every item's acceptance test is "the suite stays green", a red baseline makes every item unverifiable. T-1 is ~20 lines of import and `package.json` repair and it is a *precondition*, not a backlog item.
- **T31a second, and it is smaller than previously claimed.** The target is `dsh-v0.2.0-rc.2` — the latest **release**, and already the revision in the local checkout, so there is no checkout refresh to perform. The previous revision called this "two release lines" and listed intermediate stable versions that do not exist as releases. It remains a real bump with a real re-derivation of §2, but it is bounded, and **the 12 typecheck errors were never a rebase problem** — they reproduce identically at `0.1.1-rc.2` and at the newest tag, which is exactly why T-1 comes first.
- **T31b is an explicit decision, not a gate.** `0.2.1-alpha.1` is a pre-release and is not tracked; §9.3 records the decision so it is not silently re-opened.
- **T15 next.** It is a bug, not a gap: the guard receives an empty runId and `validateTransition` is never called, so §1 criterion 2 is not met and the §3 Outer axis was mis-described. Everything else in the enforcement family (T16, T26) is a refinement of a path that must first exist.
- **T16 next** so that the repaired guard is a declarative, reviewable policy rather than a hardcoded set — and so T7 later has one config path to expose, not two.
- **T25 early despite being "just tests"** because it is the cheapest item here and it fails today, on a real contract mismatch between `writeActionRecord` and `ts-lint.ts`. It also protects every later item from prose drift.
- **T18 + T21 form one unit.** The quiescence rule is cheap only because in-flight work is *derived* rather than tracked; and the incremental fold is what makes deriving it on every read affordable. Landing one without the other buys little.
- **T22 is the largest single cost lever**, and it is independent of everything else — it can be pulled forward if the prompt size becomes a problem before Sprint 2.
- **T17 changes the data model**, so it sits after the enforcement and legibility work and before the remaining original backlog. Its acceptance test is the parity suite: if `lock`, `status` and `lint` parity stay green, the refactor is safe.
- **T19 + T20 are the recovery pair** — identity for retries, and a bound for progress. T20 amends T3's budget.
- **T35 + T36 are the delegation pair, and they come BEFORE T19/T20.** T35 makes repair the default; T36 makes it *reachable*. Identity-for-retries and a no-progress bound both presuppose a loop that actually runs, and T35's own finding was that it did not: `delegateReview` had no callers, so every claim about retries, identity and recovery described code nothing executed. Since extraction requires **two or more** Phase-8-locked runs, T29 is untestable against an empty plane: land T30, run it twice, *then* accept T29. Landing them in the other order produces an item that appears to work and does nothing.
