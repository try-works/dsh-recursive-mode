## 1. Persistence

Persistence (persistence/Persistence.ts:62-67) is a factory, not a store: make({ storeId, timeToLive? }) returns a scoped PersistenceStore (76-102) whose get/getMany/set/setMany/remove/clear operate on schema-encoded Exit values keyed by PrimaryKey (doc 1-11). Serialization is Persistable: a request carries [symbol] = { success, error } schemas (Persistable.ts:34-49) and is built with Persistable.Class (155-213); exitSchema (223) with serializeExit (243) / deserializeExit (259) encode and decode the whole Exit, so successes and typed failures are both persisted.

Backing stores. Persistence is a codec+TTL layer over BackingPersistence (111-113), which yields BackingPersistenceStore (123-138): JSON object get/getMany/set(key,value,ttl)/setMany/remove/clear with an optional TTL. layer (152-240) applies the per-entry TimeToLiveFn (Persistable.ts:141), skips writes whose TTL is zero or negative (211, 221-222), maps an infinite TTL to undefined = no expiry (214), and background-deletes rows that fail to decode during getMany (194-206). Backends: layerBackingMemory (253); layerBackingSqlMultiTable (308, table effect_persistence_${storeId} with id/value/expires, 322-353); layerBackingSql (532, shared effect_persistence with PRIMARY KEY (store_id, id) at 542-581 plus an expires index and cleanup every 5 minutes in sqlCleanupBatchSize batches, 623-624, 692-696); layerBackingRedis (880, store id prefix, SET ... PX for finite TTLs at 944-960, Lua setManyRedis at 1000); layerBackingKvs (1048, via KeyValueStore.prefix at 1058, storing [value, expires] JSON at 1098). Composed layers: layerKvs (1146), layerMemory (1157), layerRedis (1168), layerSqlMultiTable (1179), layerSql (1190).

KeyValueStore (persistence/KeyValueStore.ts:40-97) is the plain string/binary service with make (232), makeStringOnly (277, base64 for bytes), prefix (307) and independent layers layerMemory (328), layerFileSystem (366), layerSql (509, effect_key_value_store with id/value/value_type) and layerStorage (842, Web Storage); toSchemaStore (784) gives a JSON-encoded SchemaStore (722-775). Documented gotchas: layerFileSystem clear removes the directory recursively (357-361), and keys are only distinct on case-sensitive filesystems.

PersistedQueue (persistence/PersistedQueue.ts). offer(value, { id }) deduplicates by id and the dedup record survives completion until layerCleanup removes it (82-85). take(f) claims one element, marks it complete on success, and on failure retries with the queue retry schedule until maxAttempts, then marks it failed (95-98). Delivery is explicitly at-least-once: a crash between handler success and the acknowledgement redelivers the element, so handlers must be idempotent (11-12, 67-68). Attempts are 1-based and consumed at claim time, so a process crash consumes an attempt (100-102); an interruption releases the element without counting the attempt (455-459). Elements that fail schema decoding are marked failed immediately and never surface from take (104-106). Defaults are maxAttempts 10 and Schedule.min([exponential("1 second"), spaced("5 minutes")]) (171-174); the delay is replayed from the persisted attempt count so it keeps progressing across processes (145-154, 180-197). layerCleanup (318) keeps completed elements 30 days by default and failed elements forever unless failedTimeToLive is set (304-308, 326-329), runs hourly, and should run in one instance (310-312). Stores: layerStoreMemory (516, process-local and volatile); layerStoreRedis (1277, worker locks, defaults 30 s refresh and 90 s lock expiration, 679-690); layerStoreSql (2040, default table effect_queue, 1 s poll / 30 s refresh / 2 min lock expiration, 1316-1329) with migrations, UNIQUE (id, queue_name) (1871) and a take index on (queue_name, visible_at) (2020-2027).

PersistedCache (persistence/PersistedCache.ts) reads the persisted Exit first and only on a miss runs the lookup and writes the result back with the persistent TTL (88-101). It caches the Exit, so failures are cached too. In-memory defaults are TTL 10 seconds and capacity 1024 (103-104); invalidate removes both the persisted and in-memory entries (112).

RateLimiter (persistence/RateLimiter.ts) is a store-backed quota service: consume({ algorithm: "fixed-window" | "token-bucket", onExceeded: "delay" | "fail", window, limit, key, tokens }) (52-59) with defaults tokens 1, onExceeded "fail", algorithm "fixed-window" and a 1 ms minimum window (104-107); tokens > limit fails or returns delay = window (112-130). RateLimiterStore (638-695) is the atomic primitive: fixedWindow returns [count, ttl]; tokenBucket returns [remaining, elapsedMillis] "from that single atomic operation" (651-678). Adaptive limiting adds phases "inactive" | "cooldown" | "learning" | "learned" (537) via adaptiveConsume/adaptiveFeedback (686-693). Helpers makeWithRateLimiter (263) and sleep (319) wrap effects; stores are layerStoreMemory (723) and layerStoreRedis (1394).

Redis (persistence/Redis.ts:46-66) is only an interface (send/subscribe/eval). make (80) loads Lua with SCRIPT LOAD and calls EVALSHA, refreshing on NOSCRIPT (89-119). Documented gap: Node and Deno subscribers reconnect and re-subscribe, so messages published during recovery are lost; Bun subscribers do not reconnect at all (49-55).

## 2. Cluster: entities, addresses, sharding

An Entity (cluster/Entity.ts:74-208) is a named RPC protocol: type, protocol, getShardGroup(entityId), getShardId(entityId), client, toLayer, toLayerQueue. fromRpcGroup (417) reads the shard group from the protocol's ShardGroup annotation (431); make (460) does the same from individual Rpcs. Handlers see CurrentAddress and CurrentRunnerAddress (484-504); queue handlers use Replier (518-538) and Entity.Request, which adds lastSentChunk and nextSequence for resuming streamed replies (576-603).

Addressing is four brands: EntityType (EntityType.ts:19), EntityId (EntityId.ts:19), ShardId (ShardId.ts:28-32, group plus numeric id, toString "group:id" at 125-127) and EntityAddress (EntityAddress.ts:26-30) = { shardId, entityType, entityId } with equality and hashing over all three (55-68). EntityId is the routing key: Sharding.getShardId computes Math.abs(hashString(entityId) % config.shardsPerGroup) + 1 (Sharding.ts:289-292); the default is 300 shards per group (ShardingConfig.ts:183), and shardsPerGroup should be consistent across all runners (71).

Sharding (Sharding.ts:91-215) owns assignment and routing. Each shard group has a HashRing of healthy runners weighted by Runner.weight (1245, 1281); when the healthy set changes, assignments are recomputed with HashRing.getShards(ring, config.shardsPerGroup) (1308-1324). Ownership is enforced by locks in RunnerStorage: acquiredShards is the local truth behind hasShardId and the storage read loop (277-278, 1798-1801), refreshed on shardLockRefreshInterval (default 10 s) against shardLockExpiration (35 s) (ShardingConfig.ts:187-188). Rebalancing interrupts the shards' entities, waits for lock health, then calls runnerStorage.release (Sharding.ts:328-387); waiters are resumed with EntityNotAssignedToRunner so clients re-route (346-352). Entities register while the storage read lock is held so message order is preserved (1690-1699).

Singletons are per-shard. registerSingleton builds SingletonAddress { shardId: getShardId(makeEntityId(name), shardGroup), name } (1572-1578), dies on duplicate registration (1585-1587), and starts the fiber only when the local runner has acquired that shard (1603-1606); syncSingletons starts and stops fibers as ownership moves (1617-1638). Singleton.make (Singleton.ts:48-58) wraps it in a Layer, with gotchas: a run effect that completes normally is kept alive, and failures become defects (35-40). ClusterCron (ClusterCron.ts:80-149) is built from this: a persisted, uninterruptible entity RPC run annotated with ShardGroup, an initial Singleton, and DeliverAt scheduling.

## 3. Message delivery

Message (Message.ts) has Incoming (41), IncomingRequest/IncomingRequestLocal (96, 128), IncomingEnvelope (149) and OutgoingRequest/OutgoingEnvelope (179, 212). Envelope (Envelope.ts:74) is Request | AckChunk | Interrupt; Request carries requestId, address, tag, payload, headers and trace fields (114-125), and OpaqueHole explains that cluster payloads are encoded twice (32-60). Reply (Reply.ts:54) is WithExit (final Exit) or Chunk (non-empty values plus sequence, 188-193); ReplyWithContext (91) pairs a reply with the services needed to encode it. DeliverAt (DeliverAt.ts:25-48) is a symbol protocol: a payload implementing [symbol](): DateTime schedules itself, read through toMillis (58).

MessageStorage (MessageStorage.ts:54-215) is the mailbox boundary: saveRequest/saveEnvelope/saveReply, clearReplies(requestId, { expectedReplyId }) with atomic compare-and-clear (76-86), repliesFor (un-acknowledged chunk replies plus WithExit, 88-100), unprocessedMessages(shardIds, { limit, addresses }) and unprocessedMessagesById. "Unprocessed" means requests with no WithExit reply or unacknowledged chunk replies, the latest AckChunk, and all Interrupt envelopes for unprocessed requests (150-160); only the returned messages are claimed (156-159). Dedup is by primary key: SaveResult.Duplicate carries originalId and lastReceivedReply (294-298), fed by Envelope.primaryKey (668). Persistence is opt-in per RPC via ClusterSchema.Persisted, default false (ClusterSchema.ts:47-49); Runners.notify documents that persisted messages recover replies from storage while volatile messages complete after delivery (Runners.ts:96-98).

SqlMessageStorage (SqlMessageStorage.ts) implements the Encoded driver. Dedup keys longer than the 255-character message_id column are hashed with the Crypto service (SHA-256) (99-111). Claiming is a lease: the read sets last_read to the database now and excludes rows whose last_read is newer than 10 minutes (428-488), orders by rowid (447, 455, 472), and uses FOR UPDATE where supported (373-376, 449); deliver_at gates scheduled messages (446, 471). Migration 0001 (877-1141) implies ${prefix}_messages (default prefix "cluster", 79-80) with id, rowid, message_id (UNIQUE 255), shard_id, entity_type (150), entity_id (255), kind, tag, payload, headers, trace_id, span_id, sampled, processed, request_id, reply_id, last_reply_id, last_read, deliver_at (886-907), indexed on (shard_id, processed, last_read, deliver_at) and (request_id) (988-999); and ${prefix}_replies with id, rowid, kind, request_id, payload, sequence, acked, UNIQUE (request_id, kind) and UNIQUE (request_id, sequence) (1049-1058) — at most one WithExit per request and a total order over chunks. layer needs SqlClient | ShardingConfig | Crypto and provides its own Snowflake.layerGenerator (842-848).

## 4. Runners

A Runner (Runner.ts:31-35) is RunnerAddress plus shard groups plus weight; equality ignores groups (94-96). RunnerAddress is host:port with "host:port" as primary key (RunnerAddress.ts:31-34, 69-71). The Runners service (Runners.ts:50-136) is the transport: ping, send, notify, sendLocal — documented to ensure a message hits storage before delivery to a local entity (58-61) — notifyLocal and onRunnerUnavailable, with makeRpc (555) and layerRpc (714) as the RPC implementation.

Registration and locks live in RunnerStorage (RunnerStorage.ts:32-83): register(runner, healthy) returns the MachineId, plus unregister, getRunners, setRunnerHealth and acquire/refresh/release/releaseAll. makeEncoded (155) adapts the string-encoded Encoded interface (93-144). makeMemory (208) is test-only: acquire ignores the caller and returns every shard id (228-231). SqlRunnerStorage (SqlRunnerStorage.ts:73-88) creates ${prefix}_runners (machine_id, address UNIQUE, runner, healthy, last_heartbeat) (190-232) and ${prefix}_locks (shard_id PK, address, acquired_at) (242-276); PostgreSQL and MySQL use advisory locks unless shardLockDisableAdvisory is set, otherwise lock rows (57-59, 249-267), and the advisory-lock namespace hash is "a persistent advisory-lock wire format and must never change" (33-42).

Snowflake ids are branded bigints: epoch 2025-01-01 UTC (Snowflake.ts:145), layout timestamp << 22 | (machineId % 1024) << 12 | (sequence % 4096) (175-182); Generator exposes nextUnsafe and setMachineId (93-96), and Sharding sets the machine id from RunnerStorage.register (Sharding.ts:1254-1255). MachineId is a branded Int whose out-of-range values wrap (MachineId.ts:19-24, 49-51). RunnerHealth (RunnerHealth.ts:35-40) decides whether shards may move: unresponsive runners have their shards reassigned. Options are layerNoop (54), layerPing (93; 10 s timeout, 5 retries at 500 ms) and layerK8s (143; pod readiness, and a Kubernetes API failure is treated as healthy, 105, 137). Health checking runs as the singleton "effect/cluster/Sharding/RunnerHealth", skips when there is only one runner, and never marks the last runner unhealthy (Sharding.ts:1727-1764).

## 5. Documented limitations and operational requirements

- SQL is the mainstream backend: Persistence.layerSql / layerSqlMultiTable (Persistence.ts:1179-1192), KeyValueStore.layerSql (KeyValueStore.ts:509), PersistedQueue.layerStoreSql (PersistedQueue.ts:2040), SqlMessageStorage.layer (SqlMessageStorage.ts:842), SqlRunnerStorage.layer (SqlRunnerStorage.ts:774). SingleRunner.layer still requires SqlClient and Crypto with runnerStorage "memory", because message storage is always SQL-backed (SingleRunner.ts:44-50).
- Redis is optional and caller-provided: the Redis service "does not create a Redis client itself; callers provide the client-specific operations" (Redis.ts:4-8), and pub/sub recovery loses messages (49-55).
- Clocks: TTLs use the application Clock (Persistence.ts:1206), while SQL claim leases and delayed visibility use the database clock (SqlMessageStorage.ts:361-367, PersistedQueue.ts:1341-1349); snowflake ordering depends on each runner's Clock (Snowflake.ts:9). No cluster-wide clock is required, but shard leases and queue visibility are decided by the database.
- Cluster-wide config consistency is the operator's job: ShardingConfig.layer "does not check that cluster-wide settings are consistent across runners" (ShardingConfig.ts:222-225). Defaults: maxResidentEntities 10_000, entityMailboxCapacity 4096, unprocessedMessageBatchSize 1024, entityMaxIdleTime 1 min, entityTerminationTimeout 15 s, entityRegistrationTimeout 1 min (183-201); exceeding resident capacity leaves messages in storage and fails volatile sends with MailboxFull (101-114).
- Table prefixes are load-bearing (SqlMessageStorage.ts:61-63, SqlRunnerStorage.ts:61-64), and Sharding.layer requires ShardingConfig | Runners | MessageStorage | RunnerStorage | RunnerHealth while installing its own Snowflake generator and EntityReaper (Sharding.ts:1846-1852); with MessageStorage.layerNoop persisted sends defect (1837-1838).

## 6. Standalone versus cluster-coupled

Standalone: KeyValueStore (layerMemory/layerFileSystem/layerStorage/toSchemaStore), Persistable, Persistence (layerMemory, layerKvs, layerRedis, layerSql), PersistedCache, PersistedQueue (layerStoreMemory is process-local and volatile; or layerStoreSql/layerStoreRedis), RateLimiter (layerStoreMemory or layerStoreRedis), Redis, Snowflake, MachineId, and the pure value types EntityType, EntityId, ShardId, EntityAddress, RunnerAddress, DeliverAt, Envelope, Reply, Message. There are zero imports between src/persistence and src/cluster in either direction (verified by grep), so persistence never drags in the cluster; the cluster even defines its own ClusterError.PersistenceError rather than reusing Persistence.PersistenceError.

Cluster-coupled: Entity.getShardId/client require Sharding (Entity.ts:98, 123-132); Sharding.layer pulls ShardingConfig, Runners, MessageStorage, RunnerStorage and RunnerHealth (Sharding.ts:1846-1852); Singleton.make requires Sharding (Singleton.ts:54); ClusterCron.make requires Sharding (ClusterCron.ts:79). SingleRunner.layer (SingleRunner.ts:61-79) is the middle path for one process: durable entities and workflows with no-op Runners and RunnerHealth and a SQL mailbox. MessageStorage.layerMemory (MessageStorage.ts:1230) and layerNoop (1221) swap the mailbox, but Sharding still needs the runner/lock/health wiring driven by ShardingConfig.
