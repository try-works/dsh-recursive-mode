The late-phase set, and the separate rule that actually freezes phases 6-8

Narrowing is mechanical, not a convention

A phase baseline rule whose verdict is ranked ABOVE the strictest global verdict for the same pattern is DROPPED before it can be evaluated — so no per-phase baseline can turn a global deny into an allow. The rank order is deny < ask < allow, lower being stricter, and that ordering IS the narrowing rule. No baseline rule uses the bare catch-all *, because such a rule would outrank every specific global rule at once — including recursive_lock* — and deny the phase its own tools. src/phase-rules.ts:449, src/phase-rules.ts:695

The backward loop — seven places the flow is not a straight line

This is a real property of the workflow, not a caveat. A review that comes back REVISE sends work BACK; a reopen moves the run backwards in the sequence; and the phase dependency is modelled as a GRAPH precisely because an artifact can depend on something LATER than itself. src/phase-graph.ts:2

B1REVISE → repair follow-up to the SAME child

A review round that comes back REVISE delivers a repair instruction to the SAME continuable child, whose working context is intact, and the driver waits for the re-submission. The verdict is read from `reply.md` FAIL-CLOSED: prose, an empty reply or an off-vocabulary answer becomes REVISE with a repair instruction, never a false APPROVE.

src/review-round.ts:13, src/review-round.ts:23, src/delegation.ts:413, src/recursive_review.tool.ts:48

B2The teams task board: re-audit the SAME task

`createTask` (pending) → `claim` (in_progress) → audit round → on REVISE `updateTask(edit, repair)` → re-audit the SAME task → on APPROVE `updateTask(complete)` → lock. A REJECT or the round cap RELEASES the task and fails loud: a lock NEVER happens before an APPROVE verdict.

src/teams-loop.ts:6, src/recursive_audit_team.tool.ts:55

B3reopen — the run goes BACKWARDS in the sequence

`recursive_lock` with `reopen: true` reverts a LOCKED artifact to DRAFT, invalidates every reachable downstream receipt, and re-arms the run goal. It is the ONE genuinely destructive operation, so it carries a deterministic operation id and refuses a recognised repeat.

src/recursive_lock.tool.ts:14, src/runtime.ts:1802, src/runtime.ts:1752, src/lock.ts:232

B4Stale downstream receipts — the graph remembers

A receipt records each prerequisite's hash at lock time. If an upstream artifact changes afterwards, the downstream phase is reported stale: `prerequisite '<a>' hash changed`, or `prerequisite '<a>' content changed since lock at <t>`, or `prerequisite '<a>' no longer exists`.

src/lock.ts:232, src/lock.ts:266

B5HUMAN ROUTE — `gate-block`: fix | reopen | abandon

A refused lock is a decision a person resolves. The refusal carries the three labels: `fix` (return to the phase and satisfy the gate), `reopen` (reopen an earlier locked artifact and repair it there), `abandon` (stop the run). The same payload is built in ONE place so the guard refusal and the tool refusal offer the same choice.

src/recursive_ask.tool.ts:114, src/recursive_ask.tool.ts:174, src/index.ts:601

B6Back-edges are first-class, and the graph is modelled as a graph

An `upstream-gap` addendum legitimately points at a LATER artifact — the gap was found downstream and must be closed upstream. `buildPhaseGraph` carries `addendum` edges in either direction and `backEdges()` reports them; a depth-first walk with a VISITED set is what makes reachability terminate over a cyclic graph.

src/phase-graph.ts:16, src/phase-graph.ts:100, src/phase-graph.ts:130, src/phase-graph.ts:188

B7Rule 3: an early unlocked node can be blocked by a LATER one

`nextLegalPhase` skips a LOCKED node, skips an ABSENT-and-OPTIONAL node, and then — if the first survivor has a prerequisite that is not LOCKED — returns `null`, NOT the next node. With a back-edge this is where "continue" and "blocked" give different answers, and only `null` is correct.

src/phase-graph.ts:165

Why the graph model exists at all

Three queries in the plugin are graph operations being run over a linear array: getStaleDownstreamPhases is a REACHABILITY query, getPrerequisites is an IN-EDGE query, and getNextLegalPhase is a topological walk. An array can answer all three only while the dependency happens to be linear — and the moment an artifact depends on something LATER than itself, the array model answers wrongly rather than not at all. src/phase-graph.ts:2

It is a hand-rolled graph deliberately: the item's own note records that Effect ships a stable, runtime-free Graph doing exactly this, and adopting it would trade the plugin's zero-dependency posture and its parity goldens for a few hundred lines it does not need. src/phase-graph.ts:2

The learning loop — how one run's work reaches the next

This is the cycle the whole plugin exists for, and it is a CROSS-RUN cycle: no single run can close it. A run READS the memory plane when it enters a phase; it must WRITE its own memory before phase 8 can lock; and on a re-run — with at least two locked runs and an extractor configured — it extracts training shards that the NEXT run's phase entry reads. src/memory.ts:39, src/training.ts:186

The back edge is the point. Everything else here is a step; the reason the steps exist is that the arrow at the bottom travels back to the top in a different run. That is why the plugin has a memory plane at all, and it is the part a row of phase boxes cannot show.

The read that becomes evidence: the receipt

The phase-entry read is not merely performed, it is RECORDED, and the phase-0 write gate is decided from the record rather than from the artifact text — a caller controls the text and could forge it. recordMemoryRead writes one receipt per phase entry, REPLACED rather than appended while the phase is still draft, into <run>/memory-injections.json beside the shard rows. src/memory-feedback.ts:206, src/memory-feedback.ts:50

The receipt, and what verifying the chain checks

A receipt records artifact, artifact_path, artifact_hash, locked_at, prerequisite_hashes, previous_receipt_hash and receipt_hash, at <run>/locks/<stem>.receipt.json. src/lock.ts:156

The verification is READ-ONLY deliberately — the chain is evidence, and a verification that rewrites what it verifies is worthless. Four things are checked, and one thing is explicitly NOT claimed: previous_receipt_hash chains to the SAME artifact's previous receipt, and there is exactly one receipt file per artifact, so the receipt it names has been overwritten and its LINKAGE cannot be verified from disk.
